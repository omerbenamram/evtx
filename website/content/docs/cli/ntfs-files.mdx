Give `mft_dump` the file. It works out what it is from the first bytes, and `--input-type` overrides that when it guesses wrong.

| File | What it tells you | Command |
| --- | --- | --- |
| `$Extend\$UsnJrnl:$J` | What happened to each file and when: created, written, renamed, deleted | `mft_dump -o jsonl -m '$MFT' '$J'` |
| `$I30` of a folder | What the folder held, with entries for deleted files left in its slack | `mft_dump -o csv -m '$MFT' '$I30'` |
| `$LogFile` | The most recent metadata changes, one low-level operation at a time | `mft_dump -o csv '$LogFile'` |
| `$Secure:$SDS` | The owner and access list behind each `SecurityId` in the `$MFT` | `mft_dump -o csv '$SDS'` |
| `$Boot` | Cluster size, volume size and the volume serial number | `mft_dump '$Boot'` |

If you don't know which one you need, read [Which NTFS file answers my question?](/docs/guides/ntfs-which-file) first.

## $UsnJrnl:$J

The [mft_dump page](/docs/cli/mft-dump) ends with a problem: CCleaner renamed thousands of files to `ZZZZ.ZZZ` before it deleted them, so the `$MFT` no longer knows what they were called. The change journal does. It logs a rename as two records for the same file, one with the old name and one with the new. This prints the old name of every file that was renamed to `Z`s:

```bash
mft_dump -o jsonl -m '$MFT' '$J' > usn.jsonl

jq -rn 'foreach inputs as $r (null;
    if $r.reason | test("RENAME_OLD_NAME") then $r else . end;
    select($r.reason == "USN_REASON_RENAME_NEW_NAME" and ($r.name | test("^[Z.]+$"))
           and .file_reference == $r.file_reference)
    | "\(.timestamp)  \(.full_path)")' usn.jsonl | grep -v AppData | head -n 3
```

```text
2019-01-29T23:42:09.4970995Z  Users\Steve Kowhai\Documents\Misc\Memo Things.odt
2019-01-29T23:42:09.6829486Z  Users\Steve Kowhai\Documents\Secret
2019-02-01T02:52:33.8203225Z  Users\Steve Kowhai\Documents\Misc\Package.jpg
```

858 files in all, in three sessions. Then follow one of them. `file_reference` is the file's MFT record number and sequence, and it stays the same through a rename:

```bash
jq -r 'select(.file_reference == {entry: 99814, sequence: 2})
  | [.timestamp, .name, .reason] | @tsv' usn.jsonl | tail -n 6
```

```text
2019-01-29T23:42:09.4639531Z	Memo Things.odt	USN_REASON_DATA_OVERWRITE | USN_REASON_DATA_EXTEND
2019-01-29T23:42:09.4954013Z	Memo Things.odt	USN_REASON_DATA_OVERWRITE | USN_REASON_DATA_EXTEND | USN_REASON_CLOSE
2019-01-29T23:42:09.4970995Z	Memo Things.odt	USN_REASON_RENAME_OLD_NAME
2019-01-29T23:42:09.4970995Z	ZZZZZZZZZZZ.ZZZ	USN_REASON_RENAME_NEW_NAME
2019-01-29T23:42:09.4970995Z	ZZZZZZZZZZZ.ZZZ	USN_REASON_RENAME_NEW_NAME | USN_REASON_CLOSE
2019-01-29T23:42:09.4970995Z	ZZZZZZZZZZZ.ZZZ	USN_REASON_FILE_DELETE | USN_REASON_CLOSE
```

The content was overwritten, the file was renamed, and then it was deleted, all within 60 milliseconds. That is a wipe, not someone pressing Delete.

Things to know:

- `-m '$MFT'` adds `full_path`. Without it you get the file name and the parent folder's record number only. The path is built from the `$MFT` as it is now, so a path through a folder whose record has been reused since starts with `[Orphaned]`.
- One action writes several records, with the reasons adding up until `USN_REASON_CLOSE`. Count files, not records.
- The journal is a fixed-size ring. This one holds nine days, 305,198 records. A busy server may hold a few hours.
- An exported `$J` often starts with a long run of zeros, because the file is sparse. They are skipped.

## $I30

A folder keeps an index of its files, and that index is the `$I30`. When a file is deleted its entry is removed, but the bytes stay in the slack of the index until something overwrites them. Each entry is a full `$FILE_NAME`: the name, four timestamps and the size.

```bash
mft_dump -o csv -m '$MFT' '$I30' | grep ',true,' | grep -E 'ZZZ|setuperr' | cut -d, -f5,11,13,14,18
```

```text
true,setuperr.log,Windows\setuperr.log,2019-01-29T04:26:07.6505349Z,0
true,setuperr.log,Windows\setuperr.log,2019-01-29T04:26:07.6505349Z,0
true,ZZZZZZZZZZZZZ.ZZZ,Windows\ZZZZZZZZZZZZZ.ZZZ,2019-01-28T19:46:12.5909321Z,4096
true,ZZZZZZ~1.ZZZ,Windows\ZZZZZZ~1.ZZZ,2019-01-28T19:46:12.5909321Z,4096
true,ZZZZZZZZ.ZZZ,Windows\ZZZZZZZZ.ZZZ,2019-01-28T19:40:36.9587645Z,0
```

This is the `$I30` of `C:\Windows`. The first column is `FromSlack`. The slack still holds the wiped names, and the creation time and size of the files they replaced.

An entry in slack is not always a deleted file. When NTFS rebalances an index it moves live entries and leaves their old copies behind, so 45 of the 144 entries here are from slack and most of them are folders that still exist. Check whether the name is also live before you write "deleted" in a report. A slack entry whose header was overwritten has no MFT reference, only its `$FILE_NAME`.

## $LogFile

```bash
mft_dump -o csv '$LogFile' > logfile.csv
```

One row per log record: its LSN, its transaction, the redo and undo operation, and for index changes the file name. These are five of the 26 columns:

```bash
grep swidtag logfile.csv | cut -d, -f2,5,11,12,26 | tail -n 2
```

```text
633064985,344,DeleteIndexEntryRoot,AddIndexEntryRoot,regid.1991-06.com.microsoft_Windows-10-Pro.swidtag
633065212,344,AddIndexEntryRoot,DeleteIndexEntryRoot,regid.1991-06.com.microsoft_Windows-10-Pro.swidtag
```

`-o jsonl` adds the raw redo and undo bytes of each record.

Be realistic about what this gives you. Windows overwrites `$LogFile` in a loop, so it covers the last minutes to hours before the image was taken. Most of its records are bookkeeping: of the 342,322 here, 577 carry a file name. Log records have no timestamp of their own either. It is the file to read when you need the exact order of the last operations on a volume, and the `$J` is the file to read first.

## $Secure:$SDS

NTFS stores each distinct security descriptor once, in `$Secure:$SDS`, and every file points to one by number. That number is the `SecurityId` column of `mft_dump -o csv '$MFT'`.

```bash
mft_dump -o csv '$SDS' | head -n 2
```

```text
Offset,FromMirror,SecurityId,Hash,ValidHash,Length,Owner,Group,Control,Sddl
0,false,256,0x32fec6cb,true,120,S-1-5-18,S-1-5-32-544,SE_DACL_PRESENT | SE_SELF_RELATIVE,O:S-1-5-18G:S-1-5-32-544D:(A;;0x120089;;;S-1-5-18)(A;;0x120089;;;S-1-5-32-544)
```

Join the two on `SecurityId` to get the owner and access list of every file. `-o jsonl` has each access entry spelled out, if you would rather not read SDDL.

## $Boot

```bash
mft_dump '$Boot'
```

```json
{
  "oem_id": "NTFS    ",
  "bytes_per_sector": 512,
  "sectors_per_cluster": 8,
  "cluster_size": 4096,
  "media_descriptor": 248,
  "sectors_per_track": 63,
  "number_of_heads": 255,
  "hidden_sectors": 1259520,
  "total_sectors": 61652991,
  "volume_size": 31566331392,
  "mft_lcn": 786432,
  "mft_offset": 3221225472,
  "mft_mirror_lcn": 2,
  "mft_mirror_offset": 8192,
  "mft_entry_size": 1024,
  "index_entry_size": 4096,
  "volume_serial_number": "0xE49CB2F99CB2C4F8",
  "volume_serial": "9CB2-C4F8",
  "checksum": 0

```

`volume_serial` is the number that LNK files, jump lists and prefetch files record, so it ties those to this volume. `mft_offset` is where to carve the `$MFT` from if all you have is the raw partition.
